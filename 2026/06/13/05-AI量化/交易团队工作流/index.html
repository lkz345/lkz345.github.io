CASE4 交易团队工作流（LangGraph）

一句话定位

这是一个基于 LangGraph StateGraph 编排的 AI 交易团队工作流，用 5 个角色节点（投研 Charles、信号 Zoe、风控 Kris、人审 Human、交易 Trader）模拟真实交易机构的”研究→出单→风控→审批→下单”全流程，核心亮点是条件边路由 + 人在回路 interrupt + 8 条风控规则一票否决。

整体架构

设计范式：外层 LangGraph（Workflow 模式）编排调度，内层 Charles 仍用 DeepAgents（Agent 模式）做投研分析——这就是”Workflow 编排 Agent”的混合范式。

State 设计（TradingState TypedDict）

LangGraph 的精髓是 “State as a contract”：每个节点读取它关心的字段、写回它产出的字段，字段名一旦稳定，节点之间完全解耦，可独立替换实现。

字段 所有权 类型 说明
stock_code / capital / user_question 输入 基础类型 标的、资金、用户问题
investment_view Charles 写 InvestmentView (TypedDict) stance / confidence / summary / catalysts / risks / raw_report
trade_signal Zoe 写 TradeSignal (TypedDict) direction / quantity / price / reason / backtest_winrate
risk_verdict Kris 写 RiskVerdict (TypedDict) decision / is_approved / suggested_max_pct
approved Human 写 Optional[bool] 人审结果
trade_result Trader 写 TradeResult (TypedDict) dry_run / order_id / note
retry_count / max_retry 控制流 int Kris 否决重试计数
messages 公共 Annotated[list, add] 每个节点 append 一条审计日志，LangGraph 自动合并

节点详解

Charles（投研情报官）– 383 行

职责：复用 vendor/charles_agent/ 的 DeepAgents，对标的做”国泰君安五步法”投研分析，输出完整 Markdown 研报 + 结构化 JSON 摘要。

关键设计：

  1. EXTRACT_SUFFIX 结构化提取：在用户问题末尾追加一段 JSON 模板提示，要求 Charles 在回复最后必须输出 stance / confidence / summary / catalysts / risks 的结构化摘要
  2. 双重兜底解析：_extract_view() 先尝试 regex 匹配 ```json ``` 代码块，失败后用 brace-matching 扫描所有 top-level {...} 块，从最后一个含 stance 字段的合法 JSON 中提取
  3. HTML 研报生成：_md_to_html() 轻量 Markdown 渲染 + HTML_TEMPLATE 精美模板（渐变 hero / 徽章 / 双栏催化剂+风险卡片），落盘 .md + .html 双附件到 outputs/reports/
  4. Vendor 自包含：通过 importlib.util.spec_from_file_location 显式加载 vendor 目录的 Charles agent，避免同名模块冲突

Zoe（信号官）– 208 行

职责：跑 MACD 回测获取最新信号 + 历史胜率，结合 Charles 的 investment_view 做多因子决策矩阵，输出 trade_signal。

MACD 回测调用：

  • subprocess.run 调用 scripts/run_backtest.py（vendored from 第 20 章），数据源 xtdata
  • MACD(12,26,9) 金叉/死叉信号，250 根 K 线，JSON 输出
  • _extract_json_object() 从混杂 xtdata 日志中提取最后一个合法 JSON（brace-matching）

多因子决策矩阵（Charles 基本面 + MACD 技术面）：

场景 Charles 立场 MACD 信号 决策 仓位
完全共振 bullish golden_cross buy 标准仓 _decide_position_pct
完全共振（空） bearish death_cross sell —
基本面强+技术分歧 bullish(conf≥0.7) death_cross buy 半仓（× 0.5）
技术面驱动 neutral golden_cross buy 标准仓
观望 其他组合 — hold 0

仓位计算：_decide_position_pct(stance, confidence) → bullish=30%, neutral=10%, bearish=0% × confidence。不足 1 手按 100 股最小试探单出单，交给 Kris 审批。

Kris 缩量重试：若上一轮 Kris 给了 suggested_max_pct < 1.0（WARN），Zoe 按此比例缩量重发。

Kris（风控官）– 192 行 + risk_engine.py 792 行

职责：实例化 RiskManager 跑 8 条风控规则，输出 approve / warn / reject / halt 决议。

8 条风控规则分布：

阶段 规则 逻辑 决策级别
事前 1 单笔金额上限 amount > max_order_amount（默认 capital×50%） REJECT
事前 2 价格偏离 (Price Collar) 委托价偏离现价 > 5%（防 fat finger） REJECT
事前 3 ST/黑名单 代码含 ST 或在黑名单中 REJECT
事前 4 ATR 海龟仓位 建议仓位 = (总资产 × 1%) / ATR × 价格，实际超 2 倍则 WARN WARN (带 suggested_max_pct)
事中 1 单日亏损熔断 当日净值跌幅 ≥ 2% → HALT HALT
事中 2 ATR 2N 止损 价格跌破 入场价 - 2×ATR → 强制平仓 REJECT
外部 1 事件关键词 10 个重大利空关键词（退市/立案调查/财务造假等） REJECT
外部 2 宏观 VIX 门控 VIX 阶梯映射 → 仓位系数 HALT/WARN

VIX 阶梯映射：

VIX 区间 仓位系数 风险级别
< 20 100% 正常
20-25 100%→70% 线性 焦虑
25-35 70%→30% 线性 恐慌
35-50 30%→10% 线性 极度恐慌
≥ 50 0% 末日级别，暂停开仓

审批流程（一票否决）：已熔断? → 宏观门控 → 事件关键词 → 事前 4 条 → _get_strictest() 取最严（HALT > REJECT > WARN > APPROVE）。多条 WARN 时取最小 max_position_pct。

ATR 计算：_fetch_kline_atr() subprocess 调 scripts/get_kline.py 获取 60 日 K 线，计算 ATR(14)（真实波幅均值）。

Charles→Kris 信息传递：_build_news_text() 把 Charles 的 summary + risks + catalysts 拼成新闻文本，供事件关键词检查。

Decision 枚举：APPROVE（批准）/ WARN（降仓后可执行）/ REJECT（拒绝当前订单）/ HALT（熔断停止所有交易）。WARN 的 is_approved 为 True，但携带 max_position_pct 建议缩量。

Human（人在回路）– 66 行

职责：用 LangGraph interrupt(payload) 机制硬卡住流程，把 Charles + Zoe + Kris 的全部信息抛给用户审批。

关键设计：

  • interrupt(payload) 暂停并把交易审批信息（标的/方向/数量/金额/Charles 立场/Zoe 理由/Kris 决议）抛回上层
  • 上层 graph.invoke(Command(resume=user_reply)) 恢复执行
  • 支持 dict 或字符串回复（yes/no/ok/approve/1/true → approved）
  • Workflow 模式 vs Agent 模式：Agent 想做”必须人类确认才下单”只能靠 prompt 约束（不可靠），Workflow 直接用 interrupt 在图里硬卡住，状态被 MemorySaver Checkpointer 持久化，崩溃/重启都能恢复

Trader（交易执行）– 120 行

职责：根据 trade_signal + approved 状态执行下单。

关键设计：

  • dry-run 默认开启（TRADER_DRY_RUN=1），课堂演示安全，只打印不真下单
  • 真下单走 MiniQMTTrader（vendored from 第 17 章 XtQuant 实盘接口），自动区分沪深市价类型
  • 下单前双重校验：approved == False → 跳过；direction == hold || quantity == 0 → 跳过
  • strategy_name="team-workflow", remark="LangGraph 团队工作流" 标记订单来源

条件边路由逻辑

route_after_kris

zoe_retry_bump（中转节点）

路由函数不能修改 state，所以需要一个中转节点来累加 retry_count，然后 edge 回到 Zoe。

route_after_human

主入口（main.py）– 两段式执行

  • --auto-approve 模式：自动回复 “yes” 跳过人审，方便 demo
  • _print_summary()：输出全流程汇总（Charles 立场/Zoe 信号/Kris 决议/Human 决定/Trader 结果 + 节点对话历史）

APScheduler 定时调度（scheduler.py）

  • BlockingScheduler + CronTrigger "25 9 * * 1-5"（工作日 9:25 盘前自动触发）
  • --once 手动模式，--stock / --capital / --cron 可配
  • auto_approve 默认 True（定时任务自动放行人审）
  • 运行结果序列化落盘 outputs/runs/<stock>_<date>.json（排除 raw_report 避免重复存储）
  • Workflow 模式的杀手特性：Agent 模式靠用户对话驱动；Workflow 模式可挂 cron/scheduler 自动触发，在用户睡觉/开会/出差时也能稳定执行

MemorySaver Checkpointer

  • build_graph(with_checkpointer=True) 启用内存检查点
  • 支持 interrupt 恢复：暂停 → 收集人类回复 → resume 继续
  • 支持时间旅行、状态回放
  • thread_id = run-{stock}-{pid} 隔离不同运行

技术亮点总结

  1. Workflow 编排 Agent 混合范式：Charles 内部用 DeepAgents（Agent 模式），外层由 LangGraph StateGraph（Workflow 模式）编排调度，兼得 Agent 的灵活性和 Workflow 的确定性
  2. 条件边 + 中转节点路由：Kris 否决→zoe_retry_bump 累加计数→Zoe 缩量重发，形成闭环反馈；路由函数不改 state 的设计约束通过中转节点优雅解决
  3. interrupt 人在回路：比 Agent 模式靠 prompt 约束可靠得多，硬卡住 + Checkpointer 持久化 + 崩溃恢复
  4. 8 条风控规则一票否决：事前 4 + 事中 2 + 外部 2，HALT > REJECT > WARN > APPROVE 最严优先，ATR 海龟仓位 + VIX 阶梯映射
  5. 多因子决策矩阵：Charles 基本面（stance/confidence）+ MACD 技术面（golden_cross/death_cross）联合判定，共振标准仓 / 分歧半仓 / 观望
  6. EXTRACT_SUFFIX + 双重兜底解析：regex 匹配 ```json ``` + brace-matching 扫描 {...} 块，确保从 LLM 输出中稳定提取结构化数据
  7. Vendored 自包含设计：risk_engine.py（第 19 章）、miniqmt_trader.py（第 17 章）、run_backtest.py（第 20 章）、Charles agent（vendor/）全部拷贝到本项目，可独立部署
  8. State as a contract：TradingState TypedDict + Annotated[list, add] 审计日志，节点间完全解耦
  9. APScheduler 盘前自动触发：Workflow 模式可挂 cron 定时执行，不依赖用户对话驱动
  10. dry-run 安全默认：TRADER_DRY_RUN=1 默认不真下单，演示安全
